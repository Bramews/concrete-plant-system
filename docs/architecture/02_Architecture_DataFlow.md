# 🏗️ الفصل الثاني: معمارية النظام وتدفق البيانات (Architecture & Data Flow)

## 1. المعمارية التقنية العامة (High-Level Architecture)
النظام مبني باستخدام هندسة **Full-Stack Monorepo** اعتماداً على إطار عمل Next.js. هذه المعمارية تقسم النظام إلى طبقات واضحة:

### أ. طبقة العميل (Frontend / Client Layer)
- **التقنية:** React 18+، Tailwind CSS، Framer Motion.
- **الفلسفة:** الاعتماد الكثيف على `Client Components` (باستخدام `"use client"`) للواجهات التي تتطلب تفاعلاً لحظياً مثل قمرة القيادة (Cockpit)، الموازين الحية (Live Gauges)، والإنذارات.
- **التصميم:** تم تقسيم النظام إلى واجهات مخصصة لكل دور (Role-Based UI). واجهة المحاسب تختلف جذرياً في الشكل والألوان عن واجهة المشغل (التي تستخدم نسقاً صناعياً SCADA).

### ب. طبقة الخادم (Backend / Server Layer)
- **التقنية:** Next.js Server Components، Next.js Route Handlers (`app/api/...`)، Server Actions.
- **الفلسفة:** استخدام `Server Actions` للعمليات الآمنة (مثل إنشاء `Batch` أو تحديث مخزون) لضمان عدم تعرض مفاتيح قاعدة البيانات أو المنطق التجاري للعميل. جميع الاستعلامات الثقيلة تتم في الخادم لتسريع تحميل الصفحات.

### ج. طبقة البيانات (Data Layer)
- **التقنية:** Prisma ORM، PostgreSQL / SQLite.
- **الفلسفة:** Prisma كطبقة وسيطة تضمن التوافق التام (Type-Safety) بين قاعدة البيانات والأكواد (End-to-End Type Safety).

### د. طبقة التكامل الصناعي (Hardware Integration Layer)
- **التقنية:** WebSockets، Polling، Modbus TCP/IP (عبر Node.js Micro-services أو API Routes مخصصة).
- **الفلسفة:** الخادم يتصل مباشرة بالـ PLC لقراءة المتغيرات (Tags). يقوم الخادم بمعالجة هذه الأرقام (تحويل الإشارات الكهربائية إلى أوزان فعلية) ثم يرسلها إلى المتصفح (Client) لعرضها.

## 2. تدفق البيانات (Data Flow Diagram)

لفهم كيف تتحرك البيانات، إليك المسار الكامل لدورة حياة (Batch) واحدة:

1. **الإنشاء الأولي (Creation):** 
   - موظف المبيعات يقوم بإنشاء طلب (`Order`) جديد. يتم حفظ الطلب في قاعدة البيانات بحالة `PENDING`.
2. **الاعتماد (Approval):**
   - مهندس المختبر يفحص الطلب، يحدد كود الخلطة (`MixDesign`) المناسبة، ويغير حالة الطلب إلى `LAB_APPROVED`.
3. **التجهيز للإنتاج (Preparation):**
   - في شاشة المشغل (`production/page.tsx`)، يقوم الخادم (Server Component) بجلب جميع الطلبات المعتمدة وعرضها للمشغل.
4. **التشغيل (Execution):**
   - المشغل يختار الطلب، يُدخل رقم الشاحنة واسم السائق، ويضغط على زر "إطلاق دفعة الخلط".
   - يتم استدعاء **Server Action** (`createBatch` أو ما يعادله).
5. **طبقة الأوامر الصناعية (Command Layer):**
   - الـ Server Action يقوم أولاً بالتحقق من صحة البيانات وتوفر المخزون (Validation).
   - إذا تم القبول، يرسل الخادم إشارة (Write Tag) إلى الـ PLC للبدء بوزن المواد بناءً على نسب `MixDesign`.
6. **التحديث اللحظي (Real-time Feedback):**
   - الـ PLC يبدأ بالعمل، وتتغير قيم الحساسات (الموازين).
   - الخادم يقرأ هذه القيم (عبر Polling أو WebSockets) ويمررها لمتصفح المشغل.
   - يتغير شكل `MixerStatusBar` في الواجهة من `IDLE` إلى `WEIGHING` ثم `MIXING`.
7. **الإغلاق والتسجيل (Finalization):**
   - عند انتهاء الـ PLC من التفريغ، يُرسل إشارة "اكتمل".
   - الخادم يستلم الإشارة، يقوم بإنشاء سجل `Batch` جديد في قاعدة البيانات، يخصم الكميات من مخزون الصوامع (`Material Stock`)، وينشئ تذكرة تسليم (`Ticket`).

## 3. إدارة الحالة والمزامنة (State Management & Sync)
بسبب الطبيعة اللحظية للمشروع، تم اتخاذ قرارات دقيقة بشأن إدارة الحالة:

- **الحالة الثابتة (Static Data):** مثل قوائم العملاء أو الطلبات القديمة، تُجلب وتُخزن عبر خوادم Next.js (Server Components / Caching).
- **الحالة اللحظية (Real-time Data):** أوزان الصوامع، حالة الخلاط، والإنذارات. لا تستخدم نظام Redux الثقيل، بل تعتمد على `useState` و `useEffect` بسيطة مع دوال Polling خفيفة أو WebSockets للحفاظ على أداء عالٍ (60 إطار في الثانية للرسوم المتحركة).
- **مزامنة الـ State:** عند ضغط المشغل على زر، يتم تحديث واجهة المستخدم فوراً (Optimistic UI Update) ثم يتم تأكيد العملية من الخادم.

## 4. شجرة الاعتماديات (Dependency Graph)

- `Next.js` يعتمد على `React`.
- مسارات الـ `API` و الـ `Server Actions` تعتمد على `Prisma Client`.
- الـ `Prisma Client` يعتمد على `PostgreSQL/SQLite`.
- الواجهات تعتمد بشدة على `Tailwind CSS` ومركبات مخصصة مثل `Lucide React` (للأيقونات).
- الرسوم البيانية والصوامع التفاعلية تعتمد على كود `SVG` خام مُعالج برمجياً لتجنب ثقل المكتبات الخارجية.

## 5. الريندرينغ (Rendering Flow)

1. المستخدم يطلب `/system/operator/cockpit`.
2. الخادم يقوم بـ **Server-Side Rendering (SSR)**: يجلب معلومات المستخدم الحالي، الإحصائيات اليومية، وحالة الصوامع المخزنة في قاعدة البيانات.
3. الخادم يرسل HTML جاهز للمتصفح. المتصفح يعرض الشاشة فورا (تجربة مستخدم سريعة جداً).
4. بعد ثوانٍ (Hydration)، تبدأ الـ **Client Components** (`MixerStatusBar`, `LiveGauges`) بالعمل، وتفتح قنوات الاتصال بالـ PLC لاستقبال البيانات الحية وتحديث واجهة المستخدم (مثل تحريك مستوى الأسمنت في الصومعة أو تغيير الساعة الرقمية).
