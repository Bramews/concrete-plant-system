## ☠️ القسم الأول: الأخطاء الكارثية المُوثّقة (حدثت فعلاً — ممنوع تكرارها)

### الخطأ 1: ادعاء اكتمال أنظمة بدون فحص فعلي

- **ما حدث:** سُئل الوكيل "هل نظام الحسابات مكتمل؟" فأجاب "مكتمل 100% ومربوط بالكامل" وسرد 5 ميزات تفصيلية — بدون فتح أي ملف أو تشغيل أي استعلام على قاعدة البيانات.
- **لماذا هذا كذب:** لأنه لم يتحقق فعلياً. كتب جملاً تبدو مقنعة مبنية على تخمين من أسماء المجلدات فقط.
- **القانون:** قبل القول "مكتمل" يجب:
  1. فتح ملفات الصفحات والـ actions المعنية وقراءتها
  2. تشغيل استعلام `prisma` على قاعدة البيانات للتحقق من وجود بيانات فعلية
  3. عرض النتائج الحقيقية للمستخدم بدون تجميل

### الخطأ 2: تشخيص خطأ بدون قراءة رسالة الخطأ الفعلية

- **ما حدث:** المستخدم أبلغ عن فشل حذف وتعديل المستخدمين (رسالة `Failed to remove user`). الوكيل قرأ الكود وادّعى أن السبب هو دالة `ensureNotSystemOwner` التي تمنع حذف حسابات المالك.
- **لماذا هذا غباء:** لأن المشكلة تظهر على **كل** الحسابات وليس حسابات المالك فقط. الوكيل لم يُشغّل العملية فعلياً ولم يقرأ رسالة الخطأ الحقيقية من terminal السيرفر.
- **القانون:** عند الإبلاغ عن خطأ:
  1. **أولاً:** شغّل العملية الفاشلة وراقب terminal السيرفر (`next dev` console)
  2. **ثانياً:** اقرأ رسالة الخطأ الفعلية الكاملة (stack trace)
  3. **ثالثاً:** بعد ذلك فقط شخّص السبب بناءً على الدليل

### الخطأ 3: تغيير التشخيص عند المواجهة بدون دليل

- **ما حدث:** عندما أخبر المستخدم الوكيل أن تحليله خاطئ، غيّر السبب بالكامل إلى "Foreign Key Constraint في AuditLog" — بدون أي دليل جديد. مجرد تخمين ثانٍ.
- **لماذا هذا تحايل:** لأنه لم يعترف بعدم معرفته ولم يبدأ فحصاً حقيقياً. فقط اخترع سبباً جديداً يبدو تقنياً.
- **القانون:** إذا أخبرك المستخدم أن تحليلك خاطئ:
  1. اعترف: "لا أعرف السبب الفعلي بعد"
  2. ابدأ فحصاً حقيقياً (تشغيل العملية + قراءة الخطأ + استعلام DB)
  3. لا تخترع سبباً جديداً بدون دليل

### الخطأ 4: نقل المسؤولية للمستخدم

- **ما حدث:** في كل رد، أنهى الوكيل بعبارة "قل لي عدل وسأنفذ" بدلاً من التشخيص الفوري.
- **لماذا هذا مماطلة:** لأن السؤال كان "لماذا لا يعمل؟" وليس "هل أعدّل؟". التشخيص واجب فوري.
- **القانون:** عند سؤال المستخدم عن سبب مشكلة، التشخيص الفعلي إجباري فوراً بدون انتظار إذن.

## 🔧 القسم الثاني: المشاكل البرمجية الحقيقية وطريقة إصلاحها

### المشكلة 1: فشل حذف وتعديل المستخدمين لكافة الحسابات

**الملف:** `d:\concrete-plant-system\app\actions\user-management.ts`

**السبب المُرجّح (يجب التحقق منه فعلياً أولاً):**
دالة `getAuditActor()` (سطر 11-20) تُرجع `systemOwnerId: session.userId` عندما يكون الدور `SYSTEM_OWNER`. لكن:

- `session.userId` = معرّف من جدول `User` (مثلاً `User.id = 5`)
- `AuditLog.systemOwnerId` = مفتاح أجنبي يشير إلى `SystemOwner.id` (مثلاً `SystemOwner.id = 1`)
- **هذان رقمان مختلفان من جدولين مختلفين**
- عند محاولة إدخال `User.id` كقيمة لـ `AuditLog.systemOwnerId`، تفشل العملية بخطأ قيد المفتاح الأجنبي
- هذا الخطأ يحدث داخل `try-catch` فيُرجع الرسالة العامة "Failed to remove user" أو "Failed to update member data"
- **يؤثر على كل العمليات** لأن كل عملية تحاول إنشاء سجل تدقيق

**بروتوكول الإصلاح الإجباري (خطوة بخطوة — لا تقفز):**

```
الخطوة 1: التحقق الفعلي من السبب
─────────────────────────────────
- شغّل السيرفر (npm run dev)
- افتح المتصفح وحاول حذف أي مستخدم من صفحة الشركة
- اقرأ رسالة الخطأ الكاملة من terminal السيرفر
- سجّل رسالة الخطأ الفعلية هنا قبل المتابعة

الخطوة 2: استعلام قاعدة البيانات
─────────────────────────────────
شغّل هذا الاستعلام لمعرفة الفرق بين المعرّفات:

  const session = await getSession();
  const systemOwner = await prisma.systemOwner.findFirst({
    where: { email: session.user.email }
  });
  console.log("User.id:", session.userId);
  console.log("SystemOwner.id:", systemOwner?.id);

إذا كانت الأرقام مختلفة → هذا هو السبب.
إذا كانت متطابقة → السبب مختلف، ارجع للخطوة 1 واقرأ الخطأ الفعلي.

الخطوة 3: الإصلاح (فقط بعد تأكيد السبب)
─────────────────────────────────────────
إذا تأكد أن السبب هو اختلاف المعرّفات:

عدّل دالة getAuditActor() لتجلب SystemOwner.id الحقيقي:

  async function getAuditActor() {
    const session = await getSession();
    if (!session) throw new Error("Unauthorized");
    const isSystemOwner = session.role === "SYSTEM_OWNER";

    let resolvedSystemOwnerId: number | undefined;
    if (isSystemOwner) {
      const owner = await prisma.systemOwner.findFirst({
        where: { email: session.user.email },
      });
      resolvedSystemOwnerId = owner?.id;
    }

    return {
      userId: isSystemOwner ? undefined : session.userId,
      systemOwnerId: resolvedSystemOwnerId,
      role: session.role,
    };
  }

الخطوة 4: اختبار شامل بعد الإصلاح
────────────────────────────────────
- حذف مستخدم عادي → يجب أن ينجح
- تعديل مستخدم عادي → يجب أن ينجح
- تعطيل مستخدم عادي → يجب أن ينجح
- محاولة حذف حساب مالك النظام → يجب أن يُرفض (حماية سيادية)
- npm run build → 0 أخطاء
```

## 🚀 القسم الثالث: مهام التطوير المطلوبة

### المهمة 1: البصمة الرقمية للشحنة (Delivery DNA)

**الهدف:** كل تذكرة توصيل تحمل بصمة رقمية فريدة غير قابلة للتزوير

**المطلوب بالتفصيل:**

```
1. إنشاء دالة توليد البصمة (lib/delivery-dna.ts):
   ─────────────────────────────────────────────────
   - المدخلات: orderId + mixDesignCode + quantity + driverName + truckNumber + timestamp + GPS
   - المخرجات: Hash فريد (SHA-256) + QR Code (base64)
   - كل بصمة مرتبطة بسلسلة تتابعية (Hash Chain) لمنع التلاعب بالتذاكر السابقة
   - التخزين: حقل جديد deliveryHash + qrCode في جدول DeliveryTicket

2. صفحة التحقق العامة (/verify/[hash]):
   ─────────────────────────────────────
   - صفحة عامة بدون تسجيل دخول
   - تعرض: اسم الشركة، رقم الطلب، كود الخلطة، المقاومة، الكمية، اسم السائق، التاريخ/الوقت
   - تأكيد المطابقة: ✅ "هذه الشحنة موثقة ومطابقة للمواصفات"
   - في حالة بصمة غير موجودة: ❌ "تذكرة غير معروفة"
   - التصميم: بطاقة أنيقة بتصميم النظام الحالي + شعار الشركة

3. دمج QR Code في شاشة المشغل:
   ─────────────────────────────
   - عند إصدار تذكرة توصيل، توليد البصمة تلقائياً
   - عرض QR Code في التذكرة المطبوعة
   - حفظ البصمة في قاعدة البيانات

4. قيود أمنية:
   ────────────
   - البصمة غير قابلة للتعديل بعد الإنشاء (immutable)
   - أي تلاعب بالسلسلة يُكشف تلقائياً
   - سجل تدقيق لكل عملية تحقق
```

### المهمة 2: الذكاء التنبؤي للأعطال (Predictive Maintenance)

**الهدف:** منع الأعطال المفاجئة للمعدات عبر التتبع الذكي

**المطلوب بالتفصيل:**

```
1. نموذج البيانات (Prisma Schema):
   ────────────────────────────────
   - model EquipmentMaintenance:
     - equipmentId (ربط بجدول Equipment)
     - batchCount (عداد الدفعات التراكمي)
     - maintenanceThreshold (حد الصيانة المُعدّ من الإدارة)
     - lastMaintenanceDate (تاريخ آخر صيانة)
     - nextMaintenanceDate (تاريخ الصيانة القادمة المتوقع)
     - status: HEALTHY | WARNING | CRITICAL | OVERDUE

2. محرك التتبع (lib/maintenance-engine.ts):
   ──────────────────────────────────────────
   - زيادة عداد الدفعات تلقائياً عند كل عملية صب
   - حساب النسبة المئوية للاستهلاك (batchCount / maintenanceThreshold * 100)
   - تغيير الحالة تلقائياً:
     - < 70% → HEALTHY (أخضر)
     - 70-90% → WARNING (أصفر) + تنبيه للمدير
     - 90-100% → CRITICAL (برتقالي) + تنبيه عاجل
     - > 100% → OVERDUE (أحمر) + إنذار طوارئ

3. لوحة متابعة صحة المعدات:
   ────────────────────────────
   - بطاقات ملونة لكل معدة تعرض: الاسم، عدد الدفعات، النسبة، الحالة
   - شريط تقدم بصري لكل معدة
   - ترتيب حسب الأولوية (الأكثر استهلاكاً أولاً)
   - زر "تسجيل صيانة" يُصفّر العداد ويسجل التاريخ
   - المسار: /system/manager/maintenance أو دمجها في لوحة المدير الحالية

4. نظام التنبيهات:
   ─────────────────
   - تنبيه داخل النظام (notification badge) عند وصول معدة لحالة WARNING
   - سجل تاريخي لكل عمليات الصيانة
```
